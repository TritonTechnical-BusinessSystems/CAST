- **Captured** when the user says they're planning something, OR when Claude suggests something the user doesn't explicitly decline.

### INIT-0001 — Stand up the extension's public artifacts host + rename
- **Status:** Fleshing-out · **Source:** User · **Added:** 2026-07-18 · **Revised:** 2026-07-18
- **Serves:** The extension's Chrome auto-update mechanism (`update_url` + `.crx` fetch) is the *only* thing requiring anything public at all — per `knowledge/decisions/0004-monorepo-with-artifacts-only-public-surface.md`, the extension's source stays in this private monorepo (`components/browser-extension/`); only CI-generated build output goes public.
- **Idea:** Set up an automated release step that publishes just the packaged `.crx`, `update-manifest.xml`, and the runtime rules JSON to a public host, to an **unlisted** destination (no repo browsing UI, no org listing, no links pointing to it) rather than a public GitHub repo — since there's no external-contribution use case to justify that visibility. Naming is now settled: **CAST**, same brand as the web app (previously "Triton View Manager for ConnectWise" during planning, and `TritonTechnical-BusinessSystems/TritonViewManagerForPSA` before that).
- **Fleshing-out notes:** **SIMPLIFIED 2026-07-24 — served from the app, no separate host.** Extension users are on Triton's internal network (same as the web app), and Chrome/Edge fetch the update manifest + `.crx` *from the user's browser* — so they reach **cast.tritontechnical.com** directly; the "publicly-fetchable host" premise was over-cautious for internal-only users. `update_url` is now `https://cast.tritontechnical.com/api/extension/update.xml` (`@cast/api` `routes/extension.ts` serves the gupdate manifest + `/cast.crx`). So this initiative is no longer "stand up a host" — it's just the **CRX build + sign step**: pack the extension with the signing key → `components/browser-extension/deploy/cast.crx` and bump the version in the update manifest. (Original external-host candidates kept below only if off-network users ever need them.) Legacy hosting candidates: a storage bucket/container (S3, Azure Blob, Cloudflare R2) with directory listing disabled, or GitHub Pages from a repo containing only build output. Whatever is chosen, `manifest.json`'s `update_url` must point at it permanently before the first real package ships (changing it later strands existing installs — see `knowledge/architecture/browser-extension.md` §7). A network-restricted (VPN/IP-allowlisted) host was considered as a stronger-privacy upgrade but held back as a future option, not the default — see ADR-0004's consequences. **Now covers both Chrome and Edge** (`knowledge/architecture/browser-extension.md` §8.5): separate registry namespaces and `override_update_url` policy needed for each, but likely one shared packaging/artifacts pipeline. Firefox and Shift are explicitly out of this initiative's scope — see `INIT-0010`/`INIT-0011`.
- **Related:** `knowledge/architecture/browser-extension.md`, `knowledge/decisions/0002-extension-never-touches-cw-credentials.md`, `knowledge/decisions/0004-monorepo-with-artifacts-only-public-surface.md`.

The real design question is the **config schema** shared between this app (author) and the extension (consumer). Also now covers: the reachability/timestamp-based staleness banner design and the `chrome.storage.managed` device/OS-user identity mechanism (explicitly **not** `chrome.identity.getProfileUserInfo()` — unreliable, tied to whatever personal/work account a user signs into the browser profile with) — full design in `knowledge/architecture/extension-telemetry-and-identity.md`. That file also serves the check-in catalog (`INIT-0009`).
  **Auth model settled (direction), mechanism open:** primary login is against Triton's internal/on-prem Active Directory, gated by membership in a specific AD security group (canonical name TBD — placeholder "CAST-Users" used in the mockup) — anyone outside that group is denied even with valid AD credentials. A **local account** login path (credentials stored directly in the app, independent of AD) exists as a fallback for when the AD integration itself is unreachable/broken, not as a general-purpose alternative — should be visually secondary to the AD path, not an equal-weight choice, and likely restricted to a small break-glass admin set rather than provisioned per ordinary user. **Open question, not yet decided:** the actual AD integration mechanism — options include a direct LDAP(S) bind against a domain controller, Windows Integrated Auth (Kerberos/NTLM) if the app sits fully inside the domain network, or federating through Entra ID/ADFS if Triton's on-prem AD is already synced to Entra ID. Since the app is Docker-hosted on an internal Linux VM (not Windows), LDAPS bind is the most likely low-friction fit but this needs infrastructure input before committing. Local-account password storage must follow standard secure practice (hashed + salted, e.g. bcrypt/argon2) regardless of which AD mechanism is chosen.
  **Information architecture settled (mockup):** the extension's config surfaces (role rules, expected-pod schema, fleet/check-in catalog, deployment/publish controls) live as **tabs on one "CAST Extension" page** inside this app, not separate top-level nav items. First mockup pass: `knowledge/architecture/cast-web-app-mockup.md`.
  **Stack chosen + scaffolded (2026-07-19, corrected 2026-07-20):** pnpm + turbo TypeScript monorepo (mirroring Limnode). Web app = **Vite React SPA** (`components/web`) + **Express API** (`components/api`, run via tsx) + shared `@cast/config-schema` (`packages/config-schema/`); JWT-httpOnly-cookie auth (AD LDAPS + CAST-Users gate, local bcrypt fallback), `node-cron` vessel-sync stub; deploy via nginx + docker-compose (SOC-style). Decision: `knowledge/decisions/0006-web-app-stack-vite-react-express.md` (supersedes `0005` — SvelteKit was picked before checking that the org standardizes on Vite+React+Node per SOC/Limnode). Scaffold typechecks/builds/runtime-verified (all protected routes 401 without a session). Deploy host `trt-cast-01` provisioned (`knowledge/architecture/cast-web-app-vm-provisioning.md`).
  **Remaining before this is real:** persistent stores for local break-glass accounts / config+check-in catalog (currently in-memory/stubbed — SOC uses better-sqlite3, a likely fit); build out the four extension tabs + vessel table against the mockup; run the AD bind against live AD and confirm the mechanism; resolve the VM's VLAN-egress blocker; add TLS at the deploy edge.

### INIT-0010 — Firefox support
- **Status:** Captured · **Source:** User · **Added:** 2026-07-18
- **Serves:** Broader browser coverage beyond the committed Chrome+Edge scope, if/when there's demand.
- **Idea:** Port the extension to Firefox. Explicitly deferred — not part of the current committed scope (`knowledge/architecture/browser-extension.md` §8.5).
- **Fleshing-out notes:** Genuinely separate effort, not a recompile: different engine (Gecko vs Chromium), different package format (`.xpi` vs `.crx`), mandatory Mozilla signing unless committing to Firefox ESR + a signature-bypass policy, and a different policy-delivery mechanism (`policies.json`, not a registry namespace). Mozilla's own recommended path — a self-distributed signed AMO listing, installed via a link on an internal webpage — fits the "on-demand" deployment trigger well and avoids needing ESR or registry tricks at all.
- **Related:** `knowledge/architecture/browser-extension.md`.

### INIT-0012 — Vessel Location Updating
- **Status:** In progress — the full pipeline is built end to end as of 2026-08-11: priority/tier-split engine, Vessel Site resolution (local-first, self-healing), the WS listener (Tier 1 dedicated + Tier 2 rotating, reconnect/backoff, health/backpressure monitoring), the latest-position + voyage cache, the nearest-port lookup (bundled UN/LOCODE), the nav-status mapping, and the CW Vessel Site writer (name = friendly status/destination, addressLine1 = raw coordinates). Full detail: `knowledge/architecture/vessel-location-updating-aisstream.md` §4. Every field name is now cross-confirmed correct against aisstream's own auto-generated models + a working Go reference implementation (found and fixed one real regression from an earlier, less-authoritative cross-check in the process — `MetaData` casing). **Confirmed 2026-08-11: not a CAST defect at all.** `github.com/aisstream/issues/issues/257` documents a known, ongoing, service-wide aisstream.io outage since 2026-08-05 13:31 UTC — ~15 independent developers worldwide (different accounts/regions/keys/languages) report the identical zero-message symptom. Nothing to fix on our side; CAST's pipeline is fully built and waiting. Re-check once that issue closes. **UPDATED 2026-08-17 — the outage ended, and it was masking a genuine CAST defect after all.** The "not a CAST defect" verdict above was correct about the outage being real and service-wide, but wrong to conclude there was nothing on our side: aisstream sends its JSON as **binary** WS frames, which Node's native `WebSocket` delivers as a `Blob`, so `JSON.parse(String(ev.data))` parsed the literal string `"[object Blob]"` and threw on every message. Proven, not inferred — `vessel_positions` had **0 rows ever** on production (while `checkins` had 5, ruling out the DB), and a probe run inside the `cast-api` container itself returned live frames with `constructor.name === "Blob"`. It stayed invisible because the message counters incremented *after* the parse, making an unreadable feed identical to a dead one (`0 msg/min, connected=true`), and because the listener was written 2026-08-11 — six days *after* the outage began — so it never once ran against a working feed. Fixed in `v0.9.2` (`binaryType = "arraybuffer"` + explicit decode; counters moved before the parse; new `parseFailuresTotal`/`badFrames=` gauge so this state can never be silent again). Verified end to end with the real module against the live feed: 5 frames, 0 parse failures, 5 positions stored with real coordinates. Full narrative: `knowledge/architecture/vessel-location-updating-aisstream.md` §5. **Deployed 2026-08-17 (`v0.9.2`) with `cwWritesEnabled` deliberately set to `false`** first — the fix is live on `trt-cast-01` and real positions are accumulating, but nothing reaches ConnectWise yet; that's a standing decision to review, not an oversight. **Vessel Location tab now shows this real data (`v0.10.0`, same day)** — a collapsible tree over live Tier 1/2 coverage plus per-vessel history, replacing the illustrative stub table; full detail and the position-history capture it's built on: `INIT-0033`, `knowledge/architecture/vessel-location-updating-aisstream.md` §6. **Confidence-tiered write shipped 2026-08-18 (`v0.11.0`)** — the flat-timeout behavior above is gone. Flag-country (MMSI → country of registration) was considered and explicitly declined — would sit alongside fields that all represent current location, and flag state isn't one. Full spec: `knowledge/architecture/vessel-location-updating-aisstream.md` §7, `knowledge/conventions/naming-lexicon.md`'s new **Confidence Tier** entry. The Vessel Location tab now shows a live "CW Site Name set to: …" preview line plus a Position/Destination/ETA/Last-confirmed table per vessel, driven by the identical function that produces the real write. **Controlled rollout shipped 2026-08-18 (`v0.12.0`)** — a **Vessel Site Write Allowlist** (naming-lexicon), a second gate layered on top of `cwWritesEnabled`, default empty (writes to nobody), with `"all"` as an explicit graduation sentinel.     - **Docked / anchored:** no forced decay — a vessel doesn't relocate without transmitting somewhere. Keep writing "Vessel docked in X" indefinitely off a stale position; append "(last confirmed \<date\>)" once past a short "fresh" window (proposed 2h) so the text itself signals it's presumed, not live.
    - **Underway with a stated destination + ETA:** keep writing "Vessel underway to X (ETA \_\_)" as long as now is still before ETA + a grace window (proposed 48h, for schedule slip) — don't invent "arrived," just keep the still-plausible claim. Past that window with no fresher signal, drop to unknown rather than keep asserting a destination that's now more likely wrong than right.
    - **Underway with no destination:** nothing to reason from — this is the one case where a short timeout still makes sense (today's ~6h, maybe stretched slightly for open-ocean coverage gaps).
    - **Aground:** deliberately NOT given long persistence — an incident state, not a resting state. Sitting quietly for days without escalation is the wrong instinct; this is arguably `INIT-0017` (Geo Alerts)'s job — an active alert, not passive site text — not yet reconciled between the two initiatives.
    - **Not yet decided (needs the user's call before building):** exact fresh/grace-window numbers above (2h / 48h are proposals, not commitments); whether a "presumed docked" that's aged past some very long horizon (weeks/months) should eventually surface as "needs verification" rather than persisting forever with no upper bound at all.

### INIT-0020 — Cross-platform extension delivery (macOS + Linux)
- **Status:** Fleshing-out · **Source:** User · **Added:** 2026-07-23
- **Serves:** Reach the very few Triton users on **macOS / Linux** (and unmanaged/personal Windows PCs). The current one-click installer is **Windows-only** (a `.bat` writing Chrome/Edge `ExtensionSettings` into the `HKLM` registry).
- **Key fact:** the **extension + signed CRX + self-update are already cross-platform** — they run identically on Chrome/Edge on any OS. Only the **force-install delivery** (how the managed policy is written) is OS-specific. A delivery problem, not a portability problem.
- **Per-OS mechanics:**
  - **Linux — LOW effort, no MDM/domain-join.** Chrome/Edge/Chromium honor a managed-policy JSON in `/etc/opt/chrome/policies/managed/*.json` (+ `/etc/opt/edge/...`, `/etc/chromium/...`). A `.sh` mirror of the `.bat` (served at `/api/extension/install.sh`, run with sudo) writes `ExtensionSettings` force_installed + `update_url` + `override_update_url`.
  - **macOS — Medium/High.** Force-install effectively wants **MDM** (Jamf/Intune/Kandji) pushing a `.mobileconfig`; a `defaults write` script is best-effort and unreliable without MDM. Not worth bespoke machinery for a handful.
- **Recommendation (sized to "a very few"):**
  1. **Build the Linux `.sh`** — cheap, clean, matches the Windows experience.
  2. **Unlisted Chrome Web Store listing = universal fallback** — one click, any OS/browser, no admin/policy/domain-join. Covers Mac, sudo-averse Linux, AND unmanaged/personal Windows the `.bat` can't reach. Cost: one-time store review + updates via store review (slower than self-host); unlisted = link-only. ### INIT-0032 — Public webhook receiver for CAST (TrackingMore + ConnectWise ASIO)
- **Status:** Fleshing-out — real conflict identified, one core mechanism still a placeholder · **Source:** User · **Added:** 2026-08-13
- **Serves:** Two independent, genuine needs for CAST to receive inbound webhooks: (1) TrackingMore's `TRACKING_UPDATED` push for `INIT-0018`'s shipment status (an *optimization* over polling — polling fully covers this on its own); (2) ConnectWise (via **ASIO Workflows**) firing an action into CAST when a configured trigger condition is met — this one is **not** substitutable by polling, since the whole point is reacting to a CW-side event, not discovering it after the fact on a schedule.
- **Idea:** Stand up a webhook-receiving endpoint CAST can be safely called into from outside.
- **Fleshing-out notes:**
  - **The real problem is architectural, not a sizing question.** CAST is deliberately built to **never be publicly reachable** (`knowledge/decisions/0004-monorepo-with-artifacts-only-public-surface.md`) — `cast.tritontechnical.com` has no public DNS record at all today, only a narrow `_acme-challenge` CNAME carve-out for cert issuance. A webhook is inbound-from-the-internet by definition — the opposite of that design law. This isn't something a bigger host or more RAM fixes (see `INIT-0026`'s resource-sizing pass, which found everything else comfortable).
  - **Proposed shape (not yet built):** a narrow, dedicated public surface for webhooks *only* — a separate subdomain (e.g. `webhooks.tritontechnical.com`) or a single tightly-scoped path, with a real public DNS record limited to just that, mirroring the existing `_acme-challenge` precedent of "smallest possible carve-out for a specific need" rather than reversing the policy wholesale. Plus: per-source signature/auth verification on every inbound call (TrackingMore signs its payloads SHA256 — confirmed), and nginx-level hardening (rate limiting, method/content-type restriction) on just that path.
  - **PLACEHOLDER — ConnectWise ASIO Workflows' webhook action mechanism is unconfirmed.** Needed before the receiver can be built: does an ASIO Workflow "call a webhook" action support a shared secret, HMAC signature, custom headers, or IP allowlisting for verifying the caller — or is the URL itself the only protection? Also needed: the actual payload shape. **Research attempted and blocked 2026-08-13:** local CW documentation on this box only covers the *legacy* Workflow Rules feature (`WF_NotifyActions`/`WF_NotifyEvents`/`WF_NotifyWho` — notification/email-centric, not a generic webhook action, and not ASIO); ConnectWise's own official docs page for this redirects to an authenticated `university.connectwise.com` portal with no credentials available in this session; general web search surfaced only third-party confirmation that ASIO Workflows *does* orchestration/triggers/actions, nothing with the auth/payload detail needed. **Next step: verify directly in the live ASIO Workflows UI** (or via ConnectWise University portal access) rather than guess — the security design of a public-facing endpoint shouldn't be built on an assumption.
  - **Given this reverses part of a foundational decision, it should become its own ADR once the mechanism is confirmed** (amending `0004`, or a new decision record scoped to this carve-out) — not just prose in this file, per this repo's own convention that foundational either/or choices are ADRs.

### INIT-0034 — Two real security findings surfaced during `v0.15.0`'s gate, deliberately not fixed in that release
- **Status:** Captured · **Source:** Security gate (independent re-review pass) · **Added:** 2026-08-19
- **Serves:** Tracks two genuine, live-exploitable gaps the `v0.15.0` credential-safety re-review surfaced — one pre-existing, one a narrower-than-claimed fix — that were deliberately left out of that release to avoid scope-creeping an already-large change, but must not be forgotten.
- **Idea / findings:**
  1. **CW `conditions` DSL injection, pre-existing, NOT introduced by `v0.15.0`.** `POST /api/tracking/preview` (`routes/tracking.ts`) takes `req.body` with no schema validation and passes `boards`/`statuses` strings through to `manageClient.ts`'s `queryOpenTicketActivity`/`queryOpenProjectActivity`, which build ConnectWise `conditions` query strings by escaping only `"` (`b.replace(/"/g, '\\"')`) — a value ending in a backslash escapes its own closing quote and breaks out into the surrounding condition expression. Any `requireAuth` user (not just an admin) could rewrite the filter and read company/ticket data outside the intended `market/name contains "Yacht"` scope, using Production's real credentials. Needs real fixing: proper escaping (or a parameterization-equivalent) everywhere a CW `conditions`/`customFieldConditions` string is built from request input — worth an audit across the whole file, not a one-line patch, since the same string-building pattern likely repeats.
  2. **Raw ConnectWise error bodies reach low-privileged users on more routes than just the one closed in `v0.15.0`.** `manageClient.ts`'s `cwFetch` throws `` `CW ${status}: ${body.slice(0,200)}` `` verbatim — CW's own error text, which can carry the API member/company identifier and internal CW error codes. `v0.15.0` tightened only `/api/integrations/:instance/connectwise/test` to `integrations.write`; the identical string still reaches any `requireAuth`/viewer-tier caller via `vesselIdentity.ts`, `tracking.ts`, `checkins.ts`, `logisticsShipments.ts`, `logistics.ts`, `logisticsDocuments.ts`. `logistics.ts` already has its own `cwLookupError()` sanitizer for exactly this class of issue in one place (the Carriers/Currencies routes, `v0.14.0`) — the fix is likely centralizing that pattern (or an equivalent) and applying it everywhere `e.message` from a caught CW error reaches a JSON response, not inventing a new mechanism.
  3. **Build-toolchain dependency advisories, surfaced during the per-instance-writes gate (2026-08-20), not exploitable on this deployment today.** `vite@5.4.21` has a High (`server.fs.deny` bypass via Windows ADS, dev-server-only) plus a Moderate path-traversal in optimized deps; `nanoid@3.3.16` has a High (`GHSA-2v37-7h3g-55p8`, infinite loop on `size:0`, transitive via the postcss/vite build chain, not on any API runtime path); `react-router-dom@6.30.4`/`react-router@6.30.4` carry two Moderate advisories (open redirect → XSS, and an SSR-hydration constructor-injection path CAST's client-only SPA doesn't use); `esbuild<=0.24.2` and `postcss<=8.5.22` round out the build-time Moderates. None reach the deployed nginx+API runtime (no dev server exposed, no SSR), so not urgent, but a `pnpm up` pass across the web workspace is worth scheduling rather than letting the count grow.

### INIT-0035 — In-app redeploy trigger (System Health "Redeploy" / "Update from git + Redeploy")
- **Status:** Built 2026-08-21; TWO pre-release security gate passes BLOCKED, both found real bugs, all fixed same day (below — the second pass caught that the first pass's own `.dockerignore` fix didn't actually work, verified this time with a real build-context probe, not just re-reading the pattern); first live deploy to `trt-cast-01` complete and fully verified 2026-08-21 (below) — pending only a third, hopefully final, re-verification security gate · **Source:** User · **Added:** 2026-08-21
- **Serves:** Removes the need to SSH into `trt-cast-01` and run `scripts/deploy.sh` by hand for routine deploys — directly motivated by tonight's Tailscale-on-that-VM outage, which made even reaching the box for a manual deploy a multi-step relay through the user's own VPN session.
- **Idea:** Two buttons on the System Health page — "Redeploy" (rebuild + restart from the currently checked-out code) and "Update from git + Redeploy" (`git pull --ff-only origin main` first) — gated behind a new, strict, admin-only permission.
- **Architecture decision (asked directly, user chose the safer option):** `cast-api` — the container that also decrypts every stored ConnectWise/aisstream/TrackingMore credential — must NEVER hold the real Docker socket or the git deploy key directly, since that would mean any RCE in that process could also rebuild/redeploy itself with arbitrary code from `main`. Instead:
  - **New `deploy-agent` container** (`components/deploy-agent/`) is the only thing in the stack holding either. Deliberately zero npm dependencies (`server.js` uses only Node's built-in `http`/`crypto`/`child_process`) — the single most privileged container in the stack (Docker socket access is host-root-equivalent) should have the smallest possible attack surface, including supply-chain risk from its own dependencies.
  - Exposes exactly two fixed, authenticated actions (`POST /redeploy`, `POST /update-and-redeploy`) plus a status poll (`GET /status`) on a **dedicated `deploy` Docker network**, shared only with `cast-api` — not `internal` — no `ports:` entry, unreachable from the host/internet, and `web` (the only internet-facing container) has no network path to it at all. Auth is a shared bearer token (`DEPLOY_AGENT_TOKEN`, constant-time compared), generated once, never sent to the browser.
  - The agent responds "started" immediately and runs the actual build/restart as a background child process — necessary because a redeploy tears down and rebuilds `cast-api`'s own container, so the "it started" response has to reach the browser before that happens, not after.
  - Docker socket mounted read-write (real socket, not the read-only proxy) ONLY into `deploy-agent`; `cast-api` still only ever gets the read-only proxy. The git deploy key is a NEW, dedicated key (`cast-deploy-agent-key`, generated 2026-08-21, added as a separate read-only GitHub Deploy Key on the CAST repo) — deliberately NOT a reuse of `tritonadmin`'s own interactive `cast_deploy` key, so the agent's repo access can be revoked independently. Delivered as a plain read-only bind mount at the identical host path (not Compose `secrets:` — see gate findings below for why that didn't actually work), copied to a correctly-permissioned location by `entrypoint.sh` at container start.
  - `deploy.sh` inside the agent (a variant of `scripts/deploy.sh`, not the same file — no root-check, since this container's whole purpose already requires Docker-socket-equivalent privilege) mirrors the exact same steps `tritonadmin` already runs by hand: fetch/checkout/pull (if `--pull`), sequential `docker compose build` (2 vCPU box), `docker compose up -d` with the existing retry-after-settle logic, image prune.
  - `cast-api` side: `deploy/deployAgentClient.ts` (thin fetch client, 10s timeout) + `routes/system.ts` (`GET /api/system/deploy/status`, `POST /api/system/deploy/redeploy`, `POST /api/system/deploy/update-and-redeploy`), all gated on a new `system.deploy` permission — admin-only (not bundled into `operator`/`viewer` in `auth/permissions.ts`), stricter than `integrations.write` since this triggers real host-level code execution rather than just a credential change.
  - Frontend: `DeployCard` on System Health, hidden entirely if the agent isn't configured (e.g. local dev, which has no `deploy-agent` container and no token) — polls status every 15s (3s while a deploy is actually running), confirm-modal before either action, disabled while one's in flight, shows the last run's exit code, who triggered it, and a bounded log tail.
- **Pre-release security gate BLOCKED the first version and found real, would-not-have-worked bugs, all fixed the same day, before any live test was even possible:**
  1. **The shared token could never actually reach the agent.** The original `docker-compose.yml` read `${DEPLOY_AGENT_TOKEN}` via Compose's own shell-level interpolation, which needs a `.env` in the compose *project* directory (`/opt/cast/app/.env`) — a file this deploy's layout has never had; every secret lives in `components/api/.env` instead. On the real host this would have meant the agent's own `TOKEN.length < 32` startup guard failing every time, restart-crash-looping forever. Fixed: `deploy-agent` now uses `env_file: components/api/.env`, the same file `api` already reads.
  2. **The deploy key could never actually be resolved.** Compose's `secrets: file:` mechanism is resolved by whichever `docker compose` CLI process is invoking it — which, when the agent redeploys itself, is a process running *inside the agent's own container*, not the host. The `secrets:` block's host path was never mounted into the agent, so it could never find the key. Fixed: replaced with a plain read-only bind mount at the identical host path, matching the same "mirror the host path inside the container" trick already used for `/opt/cast/app`.
  3. **A bare `docker compose up -d` would have recreated (and potentially killed) `deploy-agent` itself mid-run**, since it's part of the same compose project as `api`/`web`. Fixed: the agent's own `deploy.sh` now scopes every build/up call to `api web` explicitly — its own image is never touched by a routine app deploy, only by a manual `docker compose up -d --build deploy-agent` for the rare case the agent itself changes.
  4. **Git would have refused to run at all.** The agent runs as root against a `tritonadmin`-owned checkout; git's dubious-ownership safety check aborts on exactly that mismatch, and even past that, root-owned files written by the pull would have broken `tritonadmin`'s own manual `scripts/deploy.sh` afterward. Fixed: `git config --global --add safe.directory` in `entrypoint.sh`, plus capturing and restoring the original owner after every pull in `deploy.sh`.
  5. **A `docker-compose.yml` comment directly contradicted every other record of the key**, claiming it was tritonadmin's *reused* interactive key when it's actually a new, separately-revocable one — fixed to match reality.
  6. **This doc, the changelog, and Release Notes overclaimed the isolation** — "if compromised, still couldn't reach GitHub" is true of `cast-api`, but `deploy-agent` itself is genuinely privileged (real Docker socket + read-write access to the whole app tree, including `components/api/.env`) and was never meant to read as safe-if-compromised on its own. Language corrected everywhere to say precisely what the split buys: `cast-api`'s own attack surface can't reach Docker/git, not that the new component is secrets-free.
  7. **No audit trail existed for who triggers the single most powerful action in the app.** Fixed: the authenticated caller's identity now flows from `cast-api`'s session (`req.user`) through to the agent's status/log view (display-only — never touches `spawn`/argv), and is logged server-side on every trigger.
  8. **First-connection SSH host-key trust-on-first-use.** Fixed: GitHub's own published ED25519 host key is now pinned in the image at container start (`StrictHostKeyChecking yes` against a fixed `known_hosts`, not `accept-new`).
  9. **No recovery from a hung deploy** — fixed with a 15-minute watchdog that force-kills a stuck child process and resets state, so the buttons can't get pinned disabled forever short of an SSH session.
  10. **A separate, pre-existing High finding this change made materially worse**: no `.dockerignore` existed anywhere in the repo, so `components/api/Dockerfile`'s `COPY components/api components/api` bakes `.env` (JWT secret, LDAP bind password, break-glass password, now `DEPLOY_AGENT_TOKEN` too) — and, if a dev's local `.data/` happens to be in the build context, the encrypted-store master key and databases — straight into the `cast-api` image layer. Fixed with a root `.dockerignore` covering `.env*` (except `.env.example`), `**/.data/`, `node_modules`, `.git`, applying to every image, not just this feature.
  - Also added, proactively (not gate-found): `deploy-agent` moved off the shared `internal` network onto its own dedicated `deploy` network with only `cast-api` on it, so `web`/`docker-proxy` have no path to the agent even before its own token check.
- **First live deploy (2026-08-21, post-v0.18.0) found two more real gaps a clean local build/typecheck couldn't have caught**, neither flagged by the security gate since both are host-provisioning state, not code:
  11. **`deploy-agent` crash-looped on first boot.** Its SSH deploy key bind mount (`/home/tritonadmin/.ssh/cast-deploy-agent-key`) had never actually been provisioned on `trt-cast-01` — Docker's bind-mount behavior silently created an empty directory at that path instead of erroring, and `entrypoint.sh`'s non-recursive `cp` failed against it every restart. Masked by every container still reporting "Started"/`docker compose up` exiting 0 — only `docker inspect`'s `.State.Status` (`restarting`, not `running`) surfaced it. Fixed by generating the real keypair at that path (`ssh-keygen -t ed25519`) and force-recreating the container (`docker restart` alone doesn't work here either — Docker caches the mount's file-vs-directory type from container creation and refuses to reconcile it against the now-correct host state without a full recreate).
  12. **`DEPLOY_AGENT_TOKEN` was never actually set in production's `components/api/.env`** — same file `cast-api` also reads, so once added, both containers needed `--force-recreate` (not `restart`, which doesn't re-read `env_file` from disk) to pick it up.
  - **Verified live, post-fix:** `cast-api` healthy, `cast-deploy-agent` `running` with a clean startup log, and a real cross-network HTTP round trip from inside `cast-api` to `deploy-agent:4001` (a deliberately-wrong bearer token returned `401`, proving the `deploy` network path itself works without needing to actually trigger a build). The new deploy key's public half was added as a read-only GitHub Deploy Key on the CAST repo, then the SSH path itself verified directly (`docker exec cast-deploy-agent ssh -T git@github.com-cast` → `Hi TritonTechnical-BusinessSystems/CAST! You've successfully authenticated...`) — confirms the pinned host key + deploy key round-trip end to end against the real repo. The redeploy buttons themselves were deliberately NOT fired live — no need to trigger a self-restart just to prove the plumbing, and the 401 plus the SSH auth check plus the code review already cover it.
  - Still open: commit/tag signature verification before a pulled `main` is built and run (deliberately deferred, not solved by the SSH host-key pinning, which only protects transport — tracked here rather than silently dropped).
- **Pending before this ships:** only a third, re-verification security gate pass. All host-provisioning steps (deploy key generated and registered, `DEPLOY_AGENT_TOKEN` set) are done and live-verified as of 2026-08-21.
- **Related:** `INIT-0013` (the credential-isolation precedent this design directly extends), `knowledge/architecture/cast-web-app-deployment.md`.

### INIT-0036 — Break-glass ("TritonAdmin") password recovery, no self-service "forgot password"
- **Status:** Built 2026-08-21; TWO pre-release security gate passes BLOCKED over real gaps in an intentional-auth-bypass feature — the second pass caught that the first pass's own fix for "cleartext password in logs" was a strictly worse trade (an unattended, remotely-reachable bypass window on every fresh boot). All fixed same day — pending a third, hopefully final, re-verification gate · **Source:** User · **Added:** 2026-08-21
- **Serves:** A way back in when the break-glass local admin's password is forgotten/lost, without exposing a public self-service reset flow on the single highest-privilege account in the app.
- **Idea:** User, directly: *"Next time I log in as the local TritonAdmin breakglass account, let me do it with NO password and prompt me to set a new one."* An admin with real DB access (not a public flow) puts a local account into a **time-bound** reset-pending state (`password_hash = 'RESET_PENDING:<ISO timestamp>'`, a sentinel bcrypt never produces) via a documented `docker exec` one-liner (`knowledge/architecture/cast-web-app-auth.md`). Within 30 minutes of that timestamp, the next local-mode login for that username succeeds with ANY password including blank, and the resulting session is immediately, unavoidably routed through a mandatory "Set a new password" screen (`SetNewPassword.tsx`) before anything else works — enforced server-side (`middleware/auth.ts`'s `requireAuth`/`requirePermission` 403 every other route with `reason: "must-change-password"` while pending), not just a frontend redirect that could be navigated around.
- **Also finishes a pre-existing stub**: `local_accounts.must_change_password` has existed since the very first local-account seed (`auth/local.ts`'s `seedBreakGlass`, set whenever no `CAST_BREAKGLASS_PASSWORD` was provided) but nothing ever actually checked it anywhere until this — a freshly-generated-password account was silently never forced to change it. Now enforced identically to the deliberate reset-pending case.
- **Pre-release security gate BLOCKED the first version — this feature IS an intentional auth bypass by design, so the bar for "does it actually contain itself" is high, and the first pass didn't clear it:**
  1. **The password-change endpoint accepted any live local session with no proof of the current password and no re-check that a reset was actually pending.** A hijacked session (XSS, unattended browser) could silently rewrite the account's password permanently — not just during recovery. Separately, completing a legitimate recovery didn't invalidate a second party's session from the same armed window; they could reuse it to overwrite the password again afterward, so recovery didn't actually recover exclusive control. Fixed: voluntary changes now require the current password (`verifyLocalPassword`); recovery-path changes are atomic against the database itself (`setLocalPasswordIfResetPending` — its own `WHERE` clause re-checks the account is still reset-pending at the exact moment of the write), not just the session's JWT claim.
  2. **The armed bypass state had no expiry, no attempt cap, and no audit trail** — while armed, anyone reaching `/login` with the (repo-documented) username and any password won full admin, indefinitely, silently. Fixed: the sentinel now encodes an arm timestamp and expires after 30 minutes (fails closed, re-arm to retry); every bypass login, completed reset, and expired-window refusal is logged.
  3. **A separate, pre-existing High**: the generated break-glass password (when `CAST_BREAKGLASS_PASSWORD` was unset) was printed to the server log in cleartext. First fix: seed straight into the reset-pending state instead. **A second gate pass BLOCKED that fix specifically** — it auto-armed a live, unattended bypass window on every fresh boot / recreated data volume, reachable by anyone with network access and no human required to trigger it, a strictly worse trade than the cleartext-log problem (which at least needed log access). Refixed: seed an unknown, unlogged real password instead — the account is correctly locked until an admin runs the same attended manual procedure any locked-out account uses. The same pass also caught the expiry check failing OPEN for a future-dated timestamp (clock skew or a malformed string could grant a window that never expires) — fixed to fail closed in both directions — and a real permanent-lockout bug: an account with the legacy `must_change_password=1` flag and a REAL password would authenticate fine, then have no valid write path (the only one required the bypass sentinel it never had). Fixed by tracking, at the moment of authentication, WHICH of the two `mustChangePassword` cases applied (`viaResetBypass`) — the bypass case still uses the atomic race-guarded write; the legacy case (current password already proven via login) uses a plain write, no re-entry needed.
- **Verified live, three times** — the original happy path, the race/expiry/audit fixes, and this round's fixes (against the local dev DB, `ClaudeDev` — never `TritonAdmin`, matching this session's existing account-hygiene rule): the two-racer scenario, the 30-minute expiry in both directions (backdated AND forward-dated arm timestamps), the legacy-flag account no longer getting stuck, voluntary change correctly requiring/verifying the current password, and the full recovery round trip end to end.
- **Related:** `knowledge/architecture/cast-web-app-auth.md`.

### INIT-0038 — Deploy monitor: a live redeploy progress page that survives the redeploy
- **Status:** **COMPLETE and live 2026-08-21** (`v0.20.0`, build `2608042`) — two security-gate passes BLOCKED and were cleared, and the full round trip is verified on the real host: clicking "Update from git + Redeploy" handed off to the monitor, streamed stages live through the rebuild of the very containers serving the app, and returned to System Health on completion. Kept in Open solely for the perimeter-confirmation item below, which is a question for the network team, not a code task · **Source:** User · **Added:** 2026-08-21
- **Serves:** Makes a redeploy watchable instead of a blind ~3.5-minute wait on a dead site. Directly follows `INIT-0035` — user, after the first successful in-app deploy: *"Is it possible to have an update status page? A separate page and docker container altogether that's never impacted or replaced by active redeploy."*
- **The real gap it closes:** `deploy.sh` rebuilds `api` and `web`. `INIT-0035`'s Deploy card lived in the SPA (served by `web`) and polled through `cast-api` — so the status feed and the page displaying it went dark together, for exactly the window they existed to cover. Nothing served by `web` can ever report on `web` restarting. Verified as a real limitation before designing, not assumed.
- **Architecture (user chose the sidecar option over a front-proxy inversion, explicitly on blast-radius grounds):** a new `deploy-monitor` container publishes its own port with its own TLS, alongside `web`'s 80/443. Purely additive — if the monitor breaks, the main site is unaffected. The rejected alternative (a stable front proxy taking 80/443 and proxying to `web`) would have given same-origin cookies and one TLS point, but put a brand-new container in the critical path for ALL traffic, with no easy remote recovery if it failed and Tailscale to the box was down — which had actually happened earlier the same session.
  - **Port 20443**, at the user's direction: *"since 8443 is a little more common, in case we want to reserve it for something else later."*
  - **Least-privileged container in the stack**, deliberately, since it's the only new browser-facing surface: no Docker socket, no git deploy key, no write access to the app tree, and no `CAST_JWT_SECRET`.
  - **Why it must never hold `CAST_JWT_SECRET`:** CAST signs sessions with HS256 (symmetric, no algorithm allowlist in `jwt.verify`) — a container that can VERIFY a session can also FORGE one, including `role: "admin"`. Handing that to a browser-facing process would invert the entire point of splitting it out. Confirmed by reading `middleware/auth.ts` before designing, not assumed.
  - **Auth is a stateless HMAC watch token instead.** `cast-api`, only after `requirePermission("system.deploy")` passes, mints `<expiryMs>.<hmac>` keyed on the read-only agent token; the browser is redirected with it; the monitor recomputes and constant-time compares, and fails closed in BOTH time directions (an implausibly future-dated expiry is refused too — the same clock-skew shape that `INIT-0036`'s gate caught). No registration handshake, no shared state to survive a restart. Promoted to an httpOnly/Secure/SameSite=Strict cookie on first load so the page can strip it from the address bar.
  - **Read-only credential split on `deploy-agent`:** new `DEPLOY_AGENT_READONLY_TOKEN` is accepted on `GET /status` only; both POST routes return 403 for it. The agent refuses to start if it equals the full token, since that would make the split decorative. So the browser-facing container can watch a deploy but never start one.
  - **Stage markers, not guessed progress:** `deploy.sh` now emits `::plan::` once and `::stage::<id>` as each begins. Inferring progress from elapsed time would misreport the moment a build runs slower or faster than usual.
  - **TLS renewal self-healing:** certbot's deploy-hook reloads the `web` service by name only and knows nothing about this container, so `server.js` watches its own cert files and swaps the secure context in place. Without this it would silently serve a stale certificate ~60 days after the next renewal — a delayed-fuse bug found by reading `scripts/setup-tls.sh` during design.
  - **The monitor updates itself separately** (`update-monitor.sh`, a third fixed agent action): `deploy.sh` is scoped to `api web` precisely so it can't restart infrastructure containers mid-run, which means a routine deploy never refreshes the monitor's own image. Without an in-app path this would be SSH-only, defeating the purpose. Deliberately not folded into `deploy.sh` — rebuilding the monitor while it's streaming a deploy to someone's browser would kill that stream partway through.
- **UI direction (frontend-design skill):** an instrument panel, not a CI dashboard — deep hull-blue ground, cyan active / amber slow / red fault, drawn from marine bridge instrumentation (Triton's own field, and the right idiom for glanceable-during-a-wait). Monospace throughout at varying weight: an instrument face is uniform-width by nature, numerals must not shift as they tick, and it means the page depends on zero downloaded fonts — which matters for a page whose whole purpose is rendering when everything else is broken. The hero is elapsed time, with the progress bar explicitly labelled an estimate against a learned typical duration, switching to a "longer than usual" state rather than parking at 99% and lying. Marine *vocabulary* (UNDERWAY/MOORED) was deliberately cut — a deploy isn't a voyage, so that would have been costume rather than meaning.
- **Verified live before the gate**, against a stand-in agent replaying a realistic deploy: unauthorized/forged/expired/far-future tokens all refused (403); valid token accepted, cookie set with the right flags; SSE streaming real state; running, complete, and failed renderings; mobile reflow. **Two real bugs found and fixed by that testing, neither of which a typecheck would have caught:** landing on an ALREADY-finished deploy started the 5-second countdown and yanked the reader away (auto-return now only fires if the page actually watched the run), and a failed deploy could render every stage ✓ next to a FAILED banner (stage marking now refuses to complete-mark anything when the exit code says failed).
- **Security gate BLOCKED the first version, on a Critical that invalidated the design's central claim.** The container was documented as "least-privileged — no `CAST_JWT_SECRET`, only a read-only credential," and it used `env_file: components/api/.env` for convenience like every other service. But `env_file` loads the ENTIRE file: the one browser-facing process in the stack was therefore holding `CAST_JWT_SECRET` (HS256 — forges any admin session), `CAST_SECRET_KEY` (decrypts every stored CW/aisstream/TrackingMore credential), the LDAP bind password, **and `DEPLOY_AGENT_TOKEN`, the full trigger-capable token**. The read-only split was enforced only by which credential the code *chose to send* — not an isolation boundary at all. This had been self-flagged as a minor tradeoff ("reads exactly one variable"), which materially under-scoped it; the gate correctly re-rated it Critical. Fixed with a dedicated `components/deploy-monitor/.env` holding only the read-only token, verified via `docker compose config` showing the monitor receiving four non-secret values and nothing else.
  - That fix carried its own trap, caught immediately: a plain `env_file:` pointing at a file the host hasn't created makes EVERY `docker compose` command in the project fail — including `deploy.sh`'s own `docker compose build api`, which would have cost the box its ability to deploy at all. Resolved with `required: false`, so an un-provisioned host just leaves the monitor refusing to start (fail-closed) while everything else runs.
  - Also fixed from the same gate: no cap on concurrent SSE streams (a shareable watch token could open unbounded held-open connections on a 2 vCPU box, competing for the resources a redeploy needs — now capped at 16 with a 503); missing `Strict-Transport-Security`; and no fail-fast validation of `DEPLOY_AGENT_READONLY_TOKEN`'s length or its difference from the full token on the minting side (`config.ts` now enforces both in production).
- **A SECOND gate pass BLOCKED again — and was right that the reasoning, not just the code, was wrong.** The first fix round deferred the cookie-scoping finding as "unavoidable at the same hostname; the real fix is a separate hostname + cert." That was incorrect. Cookies are scoped by host *and path*; every route that reads `cast_token` is mounted under `/api/*` (`server.ts`), and none of the monitor's paths (`/`, `/events`, `/app.js`, `/styles.css`, `/healthz`) are. Setting `path: "/api"` on the session cookie stops the browser from ever attaching it to the monitor — same hostname, same certificate, no DNS record, no second cert. Fixed in `middleware/auth.ts`.
  - Two details that make this safe rather than a silent breakage: `res.clearCookie` only matches a cookie with the *same* path, so logout now clears both `/api` and the legacy `/` (a mismatch would have left live sessions alive in the browser on logout); and `issueSession` explicitly evicts any pre-existing `path=/` cookie before setting the scoped one, since path is part of a cookie's identity and a returning user would otherwise carry BOTH — sending two `cast_token` values on every `/api` request, with the stale broad-path one still reaching the monitor.
  - **Transition note:** an existing session keeps working (a `path=/` cookie still matches `/api`), so this forces no one to log out — but the exposure only fully closes for a given browser at its next login, when the old cookie is evicted.
  - **Verified live, not assumed** (this touches app-wide auth): login returns both the eviction and the scoped `Path=/api` cookie; `/api/auth/me` authenticates (200); the cookie is confirmed NOT sent to `/`, `/events`, `/healthz`, or `/app.js`; logout clears both paths and the session is genuinely dead (401); change-password still works under the new path; and the real SPA still authenticates in a browser with `httpOnly` intact.
  - The PDF renderer's internal cookie (`pdf/render.ts`) deliberately stays at `path: "/"` — it exists only inside an ephemeral internal Playwright context that navigates to `web:8080` and never touches the monitor, and a broad path there is one less way for a render to fail silently if a print route moves. Commented so it doesn't read as an oversight.
- **First live deploy (2026-08-21) — worked, after two provisioning gotchas, both the same root shape as `INIT-0035`'s:**
  1. `deploy-agent` reads `components/api/.env` for the new `DEPLOY_AGENT_READONLY_TOKEN`, but `env_file` applies at container **creation** — the long-running agent never saw it, so it 401'd the monitor and the page correctly showed "NO STATUS · cannot reach deploy agent."
  2. Recreating the agent still 401'd, because `--force-recreate` reuses the **existing image** and `deploy.sh` only ever builds `api web` — so the agent was running pre-`v0.20.0` code with no read-only-token support at all. The env var was there; the code ignoring it was old. Fixed with `docker compose up -d --build --force-recreate deploy-agent`. **Now documented as a standing operational rule** in `knowledge/architecture/cast-web-app-deployment.md` — any change to either infrastructure container needs an explicit `--build`.
  - **Verified live against the real agent** (not the stand-in used during development): `GET /status` with the read-only credential returns **200**, `POST /redeploy` with the same credential returns **403**. The read-only split is real on the production host, which is the single security property the container split exists to provide.
  - The monitor's failure behavior also validated itself here: it reported the unreachable agent loudly and specifically rather than showing a spinner implying progress it couldn't see.
- **Follow-up found by the user asking "how does that page ever get updated?" (fixed in `v0.20.1`, plus one gap still open):**
  - **Fixed:** "Update deploy monitor" redirected the browser to the monitor — the page that action then tears down and rebuilds. Only the two redeploy buttons had been exercised during development, never the third action added beside them. `update-monitor` now returns no watch URL and reports through the Deploy card, which stays live precisely because that action leaves `api`/`web` alone.
  - **Still open — the monitor's staleness is invisible.** Its image only changes on an explicit `--build`, so after any `git pull` touching `components/deploy-monitor/`, the running container silently lags the source and nothing in the UI says so. Worth surfacing the monitor's built version on the Deploy card (it already reports `/healthz`; that could carry a build stamp) and flagging when it differs from the app's, so "Update deploy monitor" becomes a prompted action rather than something you have to remember. Low urgency — the monitor is ~300 lines with no dependencies and changes rarely — but it's a real drift path.
- **Open item that is NOT a code fix — needs human verification before/at deploy:**
  1. **Perimeter exposure of the new port.** `trt-cast-01` is documented "inbound no," but there's no host-level `ufw`/`iptables` in the provisioning record — the block is upstream at the `10.20.30.1` gateway, managed by the network team, not represented in any repo artifact. Whether that's a blanket default-deny (safe) or an 80/443-specific allowlist (in which case `20443` may or may not be covered) can't be determined from the repo and must be confirmed with whoever controls that perimeter.
- **Remaining accepted tradeoffs:** runs as root, solely because certbot's archive is `0700 root:root` and the TLS private key is otherwise unreadable. And the watch token is a shareable, non-single-use bearer link for 30 minutes — anyone with the URL can watch that deploy's build/git output (inspected: contains no secrets).
- **Related:** `INIT-0035` (the redeploy trigger this completes), `knowledge/architecture/cast-web-app-deployment.md`.
