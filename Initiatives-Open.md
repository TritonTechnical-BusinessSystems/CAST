- **Captured** when the user says they're planning something, OR when Claude suggests something the user doesn't explicitly decline.

### INIT-0001 — Stand up the extension's public artifacts host + rename
- **Status:** Fleshing-out · **Source:** User · **Added:** 2026-07-18 · **Revised:** 2026-07-18
- **Serves:** The extension's Chrome auto-update mechanism (`update_url` + `.crx` fetch) is the *only* thing requiring anything public at all — per `knowledge/decisions/0004-monorepo-with-artifacts-only-public-surface.md`, the extension's source stays in this private monorepo (`components/browser-extension/`); only CI-generated build output goes public.
- **Idea:** Set up an automated release step that publishes just the packaged `.crx`, `update-manifest.xml`, and the runtime rules JSON to a public host, to an **unlisted** destination (no repo browsing UI, no org listing, no links pointing to it) rather than a public GitHub repo — since there's no external-contribution use case to justify that visibility. Naming is now settled: **CAST**, same brand as the web app (previously "Triton View Manager for ConnectWise" during planning, and `TritonTechnical-BusinessSystems/TritonViewManagerForPSA` before that).
- **Fleshing-out notes:** **SIMPLIFIED 2026-07-24 — served from the app, no separate host.** Extension users are on Triton's internal network (same as the web app), and Chrome/Edge fetch the update manifest + `.crx` *from the user's browser* — so they reach **cast.tritontechnical.com** directly; the "publicly-fetchable host" premise was over-cautious for internal-only users. `update_url` is now `https://cast.tritontechnical.com/api/extension/update.xml` (`@cast/api` `routes/extension.ts` serves the gupdate manifest + `/cast.crx`). So this initiative is no longer "stand up a host" — it's just the **CRX build + sign step**: pack the extension with the signing key → `components/browser-extension/deploy/cast.crx` and bump the version in the update manifest. (Original external-host candidates kept below only if off-network users ever need them.) Legacy hosting candidates: a storage bucket/container (S3, Azure Blob, Cloudflare R2) with directory listing disabled, or GitHub Pages from a repo containing only build output. Whatever is chosen, `manifest.json`'s `update_url` must point at it permanently before the first real package ships (changing it later strands existing installs — see `knowledge/architecture/browser-extension.md` §7). A network-restricted (VPN/IP-allowlisted) host was considered as a stronger-privacy upgrade but held back as a future option, not the default — see ADR-0004's consequences. **Now covers both Chrome and Edge** (`knowledge/architecture/browser-extension.md` §8.5): separate registry namespaces and `override_update_url` policy needed for each, but likely one shared packaging/artifacts pipeline. Firefox and Shift are explicitly out of this initiative's scope — see `INIT-0010`/`INIT-0011`.
- **Related:** `knowledge/architecture/browser-extension.md`, `knowledge/decisions/0002-extension-never-touches-cw-credentials.md`, `knowledge/decisions/0004-monorepo-with-artifacts-only-public-surface.md`.

### INIT-0008 — CAST web app (centralized configuration UI)
- **Status:** In progress (scaffolded) · **Source:** User · **Added:** 2026-07-18 · **Revised:** 2026-07-19
- **Serves:** Replaces the extension's planning-phase manual "Design Mode export → commit JSON → host on GitHub raw URL" workflow (`knowledge/architecture/browser-extension.md` §5) with a real centralized configuration surface. Always developed in lockstep with the extension — this pairing is why CAST is one monorepo (`knowledge/decisions/0004-monorepo-with-artifacts-only-public-surface.md`), alongside the scheduled data-sync component (`INIT-0002`).
- **Idea:** A web-based interface for centrally configuring the extension's role/department rules (hide/show/reorder/move, expected-pod lists) instead of hand-editing and committing JSON.
- **Fleshing-out notes:** **Hosting settled:** internal Linux VM, deployed via Docker, reachable at `cast.tritontechnical.com`. Tech stack itself still undecided (`INIT-0002`'s sibling — likely shares a stack once one is chosen). The real design question is the **config schema** shared between this app (author) and the extension (consumer). Not yet decided: where the schema is defined/versioned, and how this app pushes an updated config out to the extension's public artifacts host (`INIT-0001`) — presumably the same release step that publishes the `.crx`. Also now covers: the reachability/timestamp-based staleness banner design and the `chrome.storage.managed` device/OS-user identity mechanism (explicitly **not** `chrome.identity.getProfileUserInfo()` — unreliable, tied to whatever personal/work account a user signs into the browser profile with) — full design in `knowledge/architecture/extension-telemetry-and-identity.md`. That file also serves the check-in catalog (`INIT-0009`).
  **Auth model settled (direction), mechanism open:** primary login is against Triton's internal/on-prem Active Directory, gated by membership in a specific AD security group (canonical name TBD — placeholder "CAST-Users" used in the mockup) — anyone outside that group is denied even with valid AD credentials. A **local account** login path (credentials stored directly in the app, independent of AD) exists as a fallback for when the AD integration itself is unreachable/broken, not as a general-purpose alternative — should be visually secondary to the AD path, not an equal-weight choice, and likely restricted to a small break-glass admin set rather than provisioned per ordinary user. **Open question, not yet decided:** the actual AD integration mechanism — options include a direct LDAP(S) bind against a domain controller, Windows Integrated Auth (Kerberos/NTLM) if the app sits fully inside the domain network, or federating through Entra ID/ADFS if Triton's on-prem AD is already synced to Entra ID. Since the app is Docker-hosted on an internal Linux VM (not Windows), LDAPS bind is the most likely low-friction fit but this needs infrastructure input before committing. Local-account password storage must follow standard secure practice (hashed + salted, e.g. bcrypt/argon2) regardless of which AD mechanism is chosen.
  **Information architecture settled (mockup):** the extension's config surfaces (role rules, expected-pod schema, fleet/check-in catalog, deployment/publish controls) live as **tabs on one "CAST Extension" page** inside this app, not separate top-level nav items. First mockup pass: `knowledge/architecture/cast-web-app-mockup.md`.
  **Stack chosen + scaffolded (2026-07-19, corrected 2026-07-20):** pnpm + turbo TypeScript monorepo (mirroring Limnode). Web app = **Vite React SPA** (`components/web`) + **Express API** (`components/api`, run via tsx) + shared `@cast/config-schema` (`packages/config-schema/`); JWT-httpOnly-cookie auth (AD LDAPS + CAST-Users gate, local bcrypt fallback), `node-cron` vessel-sync stub; deploy via nginx + docker-compose (SOC-style). Decision: `knowledge/decisions/0006-web-app-stack-vite-react-express.md` (supersedes `0005` — SvelteKit was picked before checking that the org standardizes on Vite+React+Node per SOC/Limnode). Scaffold typechecks/builds/runtime-verified (all protected routes 401 without a session). Deploy host `trt-cast-01` provisioned (`knowledge/architecture/cast-web-app-vm-provisioning.md`).
  **Remaining before this is real:** persistent stores for local break-glass accounts / config+check-in catalog (currently in-memory/stubbed — SOC uses better-sqlite3, a likely fit); build out the four extension tabs + vessel table against the mockup; run the AD bind against live AD and confirm the mechanism; resolve the VM's VLAN-egress blocker; add TLS at the deploy edge.

### INIT-0010 — Firefox support
- **Status:** Captured · **Source:** User · **Added:** 2026-07-18
- **Serves:** Broader browser coverage beyond the committed Chrome+Edge scope, if/when there's demand.
- **Idea:** Port the extension to Firefox. Explicitly deferred — not part of the current committed scope (`knowledge/architecture/browser-extension.md` §8.5).
- **Fleshing-out notes:** Genuinely separate effort, not a recompile: different engine (Gecko vs Chromium), different package format (`.xpi` vs `.crx`), mandatory Mozilla signing unless committing to Firefox ESR + a signature-bypass policy, and a different policy-delivery mechanism (`policies.json`, not a registry namespace). Mozilla's own recommended path — a self-distributed signed AMO listing, installed via a link on an internal webpage — fits the "on-demand" deployment trigger well and avoids needing ESR or registry tricks at all.
- **Related:** `knowledge/architecture/browser-extension.md`.

### INIT-0012 — Vessel Location Updating
- **Status:** In progress — the full pipeline is built end to end as of 2026-08-11: priority/tier-split engine, Vessel Site resolution (local-first, self-healing), the WS listener (Tier 1 dedicated + Tier 2 rotating, reconnect/backoff, health/backpressure monitoring), the latest-position + voyage cache, the nearest-port lookup (bundled UN/LOCODE), the nav-status mapping, and the CW Vessel Site writer (name = friendly status/destination, addressLine1 = raw coordinates). Full detail: `knowledge/architecture/vessel-location-updating-aisstream.md` §4. Every field name is now cross-confirmed correct against aisstream's own auto-generated models + a working Go reference implementation (found and fixed one real regression from an earlier, less-authoritative cross-check in the process — `MetaData` casing). **Confirmed 2026-08-11: not a CAST defect at all.** `github.com/aisstream/issues/issues/257` documents a known, ongoing, service-wide aisstream.io outage since 2026-08-05 13:31 UTC — ~15 independent developers worldwide (different accounts/regions/keys/languages) report the identical zero-message symptom. Nothing to fix on our side; CAST's pipeline is fully built and waiting. Re-check once that issue closes. **UPDATED 2026-08-17 — the outage ended, and it was masking a genuine CAST defect after all.** The "not a CAST defect" verdict above was correct about the outage being real and service-wide, but wrong to conclude there was nothing on our side: aisstream sends its JSON as **binary** WS frames, which Node's native `WebSocket` delivers as a `Blob`, so `JSON.parse(String(ev.data))` parsed the literal string `"[object Blob]"` and threw on every message. Proven, not inferred — `vessel_positions` had **0 rows ever** on production (while `checkins` had 5, ruling out the DB), and a probe run inside the `cast-api` container itself returned live frames with `constructor.name === "Blob"`. It stayed invisible because the message counters incremented *after* the parse, making an unreadable feed identical to a dead one (`0 msg/min, connected=true`), and because the listener was written 2026-08-11 — six days *after* the outage began — so it never once ran against a working feed. Fixed in `v0.9.2` (`binaryType = "arraybuffer"` + explicit decode; counters moved before the parse; new `parseFailuresTotal`/`badFrames=` gauge so this state can never be silent again). Verified end to end with the real module against the live feed: 5 frames, 0 parse failures, 5 positions stored with real coordinates. Full narrative: `knowledge/architecture/vessel-location-updating-aisstream.md` §5. **Deployed 2026-08-17 (`v0.9.2`) with `cwWritesEnabled` deliberately set to `false`** first — the fix is live on `trt-cast-01` and real positions are accumulating, but nothing reaches ConnectWise yet; that's a standing decision to review, not an oversight. **Vessel Location tab now shows this real data (`v0.10.0`, same day)** — a collapsible tree over live Tier 1/2 coverage plus per-vessel history, replacing the illustrative stub table; full detail and the position-history capture it's built on: `INIT-0033`, `knowledge/architecture/vessel-location-updating-aisstream.md` §6. **Confidence-tiered write shipped 2026-08-18 (`v0.11.0`)** — the flat-timeout behavior above is gone. Three tiers (🟢 current / 🔵 presumed / 🟠 stale), reverting to a bare "Vessel" past a configurable fallback (default 90 days) with nothing fresher; a new "Last AIS Data Update" custom field on the Site tracks true last-confirmed time in every tier; the Site's **Time Zone** is now also resolved and written from coordinates (a real CW `timeZoneSetups` reference, not IANA — 94 fixed entries, matched by live-computed offset + geographic tiebreak). Flag-country (MMSI → country of registration) was considered and explicitly declined — would sit alongside fields that all represent current location, and flag state isn't one. Full spec: `knowledge/architecture/vessel-location-updating-aisstream.md` §7, `knowledge/conventions/naming-lexicon.md`'s new **Confidence Tier** entry. The Vessel Location tab now shows a live "Will write: …" preview line plus a Position/Destination/ETA/Last-confirmed table per vessel, driven by the identical function that produces the real write. · **Source:** User · **Added:** 2026-07-18
- **Serves:** First concrete instance of the scheduled data-sync component (`INIT-0002`) — capability ConnectWise doesn't natively provide (live vessel position/status), pulled server-side and pushed back into CW via its credentialed API, never client-side. - **Idea:** Each ConnectWise company (client) record that represents a vessel carries a custom field holding its **IMO number** (the vessel's permanent international identifier). On a schedule, for clients in a specific status, resolve each vessel's live AIS data and write back a **human-friendly navigational status** ("Moored / At anchor / Under way") plus an **appropriate friendly location** (nearest port/anchorage, or destination when under way). *(Refined 2026-07-22: the output is friendly status + place name, **not** a street address — so the target is almost certainly two custom fields, not a location record's address field; see the architecture note.)*
- **Fleshing-out notes:**
  - **Data source & legality — DECIDED (2026-07-22): aisstream.io.** A colleague found aisstream.io, a **free, legitimate AIS WebSocket API** — this resolves the original blocker (MarineTraffic's ToS prohibits scraping). Key stored server-side (`components/api/.env`, `CAST_AISSTREAM_API_KEY`). Full model + design consequences captured in `knowledge/architecture/vessel-location-updating-aisstream.md`. **This changes the architecture materially:** it's a *push stream, not a lookup*, so the feature becomes a long-lived WS listener (latest-position cache) + the scheduled writer; positions are keyed by **MMSI not IMO** (IMO only in `ShipStaticData`) so an IMO↔MMSI mapping is needed; positions are lat/lon so an address write needs reverse-geocoding; and AIS nav-status doesn't map 1:1 to docked/moored/dry-docked/underway.     - **Docked / anchored:** no forced decay — a vessel doesn't relocate without transmitting somewhere. Keep writing "Vessel docked in X" indefinitely off a stale position; append "(last confirmed \<date\>)" once past a short "fresh" window (proposed 2h) so the text itself signals it's presumed, not live.
    - **Underway with a stated destination + ETA:** keep writing "Vessel underway to X (ETA \_\_)" as long as now is still before ETA + a grace window (proposed 48h, for schedule slip) — don't invent "arrived," just keep the still-plausible claim. Sitting quietly for days without escalation is the wrong instinct; this is arguably `INIT-0017` (Geo Alerts)'s job — an active alert, not passive site text — not yet reconciled between the two initiatives.
    - **Not yet decided (needs the user's call before building):** exact fresh/grace-window numbers above (2h / 48h are proposals, not commitments); whether a "presumed docked" that's aged past some very long horizon (weeks/months) should eventually surface as "needs verification" rather than persisting forever with no upper bound at all.

### INIT-0020 — Cross-platform extension delivery (macOS + Linux)
- **Status:** Fleshing-out · **Source:** User · **Added:** 2026-07-23
- **Serves:** Reach the very few Triton users on **macOS / Linux** (and unmanaged/personal Windows PCs). The current one-click installer is **Windows-only** (a `.bat` writing Chrome/Edge `ExtensionSettings` into the `HKLM` registry).

- **Per-OS mechanics:**
  - **Linux — LOW effort, no MDM/domain-join.** Chrome/Edge/Chromium honor a managed-policy JSON in `/etc/opt/chrome/policies/managed/*.json` (+ `/etc/opt/edge/...`, `/etc/chromium/...`). - **Recommendation (sized to "a very few"):**
  1. **Build the Linux `.sh`** — cheap, clean, matches the Windows experience.
  2. **Unlisted Chrome Web Store listing = universal fallback** — one click, any OS/browser, no admin/policy/domain-join. Covers Mac, sudo-averse Linux, AND unmanaged/personal Windows the `.bat` can't reach. Cost: one-time store review + updates via store review (slower than self-host); unlisted = link-only. For MDM-managed Macs, a pushed `.mobileconfig` is the clean alternative.
- **Net:** Linux `.sh` + Unlisted Web Store covers 100% of users with minimal build; self-hosted force-install stays the default for AD-joined Windows.

### INIT-0032 — Public webhook receiver for CAST (TrackingMore + ConnectWise ASIO)
- **Status:** Fleshing-out — real conflict identified, one core mechanism still a placeholder · **Source:** User · **Added:** 2026-08-13
- **Serves:** Two independent, genuine needs for CAST to receive inbound webhooks: (1) TrackingMore's `TRACKING_UPDATED` push for `INIT-0018`'s shipment status (an *optimization* over polling — polling fully covers this on its own); (2) ConnectWise (via **ASIO Workflows**) firing an action into CAST when a configured trigger condition is met — this one is **not** substitutable by polling, since the whole point is reacting to a CW-side event, not discovering it after the fact on a schedule.
- **Idea:** Stand up a webhook-receiving endpoint CAST can be safely called into from outside.
- **Fleshing-out notes:**
  - **The real problem is architectural, not a sizing question.** CAST is deliberately built to **never be publicly reachable** (`knowledge/decisions/0004-monorepo-with-artifacts-only-public-surface.md`) — `cast.tritontechnical.com` has no public DNS record at all today, only a narrow `_acme-challenge` CNAME carve-out for cert issuance. A webhook is inbound-from-the-internet by definition — the opposite of that design law. This isn't something a bigger host or more RAM fixes (see `INIT-0026`'s resource-sizing pass, which found everything else comfortable).
  - **Proposed shape (not yet built):** a narrow, dedicated public surface for webhooks *only* — a separate subdomain (e.g. `webhooks.tritontechnical.com`) or a single tightly-scoped path, with a real public DNS record limited to just that, mirroring the existing `_acme-challenge` precedent of "smallest possible carve-out for a specific need" rather than reversing the policy wholesale. Plus: per-source signature/auth verification on every inbound call (TrackingMore signs its payloads SHA256 — confirmed), and nginx-level hardening (rate limiting, method/content-type restriction) on just that path.
  - **PLACEHOLDER — ConnectWise ASIO Workflows' webhook action mechanism is unconfirmed.** Needed before the receiver can be built: does an ASIO Workflow "call a webhook" action support a shared secret, HMAC signature, custom headers, or IP allowlisting for verifying the caller — or is the URL itself the only protection? Also needed: the actual payload shape. **Research attempted and blocked 2026-08-13:** local CW documentation on this box only covers the *legacy* Workflow Rules feature (`WF_NotifyActions`/`WF_NotifyEvents`/`WF_NotifyWho` — notification/email-centric, not a generic webhook action, and not ASIO); ConnectWise's own official docs page for this redirects to an authenticated `university.connectwise.com` portal with no credentials available in this session; general web search surfaced only third-party confirmation that ASIO Workflows *does* orchestration/triggers/actions, nothing with the auth/payload detail needed. **Next step: verify directly in the live ASIO Workflows UI** (or via ConnectWise University portal access) rather than guess — the security design of a public-facing endpoint shouldn't be built on an assumption.
  - **Given this reverses part of a foundational decision, it should become its own ADR once the mechanism is confirmed** (amending `0004`, or a new decision record scoped to this carve-out) — not just prose in this file, per this repo's own convention that foundational either/or choices are ADRs.
- **Related:** `INIT-0018`, `INIT-0026`, `knowledge/decisions/0004-monorepo-with-artifacts-only-public-surface.md`, `knowledge/architecture/shipment-tracking-trackingmore.md`.

### INIT-0033 — Long-standing AIS position history for fleet analytics
- **Status:** In progress — storage/capture + a first read surface built 2026-08-17 (`v0.10.0`); retention policy and a real analytics surface still open · **Source:** User · **Added:** 2026-08-17
- **Serves:** `INIT-0012`'s pipeline used to keep **latest-position-only** (one row per vessel, overwritten on every update) — a deliberate scope boundary drawn when the pipeline was designed (`knowledge/architecture/vessel-location-updating-aisstream.md` §3.1: "position-*history* ... remains a genuinely separate, not-yet-needed concern"). This initiative is that boundary revisited, now that the pipeline is live and the question has a concrete shape.
- **Idea:** Retain vessel position/status over time (not just the current snapshot) to answer questions the live view can't: how long a refit actually took at a given yard, which yards/ports a client's vessel keeps returning to, how much of the year a vessel spends underway vs. dockside. User's framing: this doesn't need to cover the whole tracked fleet if storage were a real constraint — but a same-session estimate found it isn't one.
- **Fleshing-out notes:**
  - **Storage is not the constraining factor — confirmed with numbers, not assumed.** Two designs estimated against the then-current 201-vessel eligible fleet and the SQLite/`cast.db` setup: raw ping logging (~5.7 GB/year, low analytic value) vs. hourly snapshot + change-event logging (~317 MB/year, recommended). Full estimate: `knowledge/architecture/vessel-location-updating-aisstream.md` §6.
  - **Built 2026-08-17 (`v0.10.0`) — storage/capture side, a THIRD design, not either estimated above.** New insert-only `vessel_position_history` table (`components/api/src/store/db.ts`), written alongside every `vessel_positions` upsert (`positionStore.ts`) — one row per **real AIS update actually received**, not a synthetic hourly heartbeat or raw-ping log. Simpler than the hourly-heartbeat design (no separate timer, no "did we already snapshot this hour" bookkeeping) and cheaper than either estimate above, since the fleet's real observed delivery rate is sparser than either estimate assumed. Trade-off accepted knowingly: a vessel that goes genuinely silent for weeks (the shipyard-dark scenario from the same day's staleness-design conversation, still unbuilt — see `INIT-0012`) produces a real *gap* in its history rather than a heartbeat confirming "still there, no news" — acceptable for today's use (inspecting what's been received), revisit if a future retention/gap-filling need makes the hourly design worth the extra bookkeeping.
  - **First read surface built the same day: the Vessel Location tab** (`pages/Vessel.tsx`) — a collapsible tree, one row per Tier 1/2 vessel, current status via the same `formatSiteUpdate()` the real CW write uses, expandable to its most recent received updates (`GET /api/vessels/history/:mmsi?limit=N`, default 20). This is inspection, not yet analytics — no refit-duration or recurring-yard report exists; that's still a real, unstarted piece of this initiative's original "Idea."
  - **Still open, not yet decided:** retention policy (currently unbounded — nothing ages out; the storage math says that's affordable, but "affordable" isn't the same as "decided"); whether the real analytics surface (refit duration, recurring yards, underway-vs-dockside time) becomes a CAST web app page, an export, or stays ad hoc SQL until a concrete report is requested; whether history should start from every vessel with a valid MMSI or stay scoped to Tier 1/2 coverage only (currently the latter, since only Tier 1/2 vessels ever receive AIS data at all under the priority engine).
- **Related:** `INIT-0012`, `knowledge/architecture/vessel-location-updating-aisstream.md`.
